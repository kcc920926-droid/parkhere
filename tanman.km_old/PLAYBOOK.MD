| 질문 | 탄만큼의 답 | 보여줄 증거 |
| --- | --- | --- |
| 차량 이용자의 어떤 문제를 해결하는가? | 함께 이동해도 탑승 구간이 달라 비용 계산이 번거롭고, 금액을 요청하는 대화가 어색하다. | 중간 하차자가 있는 동행의 기존 정산과 구간 정산 비교 |

핵심 차별점은 **차량이 비용 산정의 근거를 제공한다는 것**이다. QR 송금은 이 경험을 마무리하는 수단이다.

`TANMAN.KM`은 브랜드 표기다. 도메인 소유권이나 상표 등록이 확인된 이름으로 표현하지 않는다. 과거 아이디어명인 RideSplit은 이후 제품 화면과 제출 자료에서 탄만큼으로 통일한다.

### 사용자와 첫 번째 장면

초기 대상은 친구 여행, 동료 카풀, 동호회 이동처럼 이미 관계가 있는 사람들의 동행이다. 첫 시연은 **운전자 D와 동승자 A·B가 출발하고, A가 중간에 내리는 상황**으로 고정한다.

검증할 가설은 다음과 같다.

- 서로 다른 탑승 구간을 반영하면 일괄 균등 분담보다 수용하기 쉬운가?
- 각자의 금액이 나온 이유를 보면 계산을 다시 확인하는 대화가 줄어드는가?
- QR 등록과 하차 확인이 수동 계산보다 충분히 간단한가?
- 반복 이용할 상황이 있는가? 실제 사용 빈도와 지불 의향은 아직 검증되지 않았다.

## 3. MVP 범위와 우선순위

아래 우선순위는 구현 기본안이다. **P0의 전체 흐름이 작동한 뒤 P1을 추가한다.**

**MVP의 구간 기록은 확인된 탑승자 등록 + 사람별 ‘내려요’ + 경계별 누적 주행거리로 구성한다.** 출발·중간 합류 때 탑승을 확인하고, 하차 버튼·전체 종료 때 해당 구간을 닫는다. 금액 계산에는 별도로 합의한 연비·유가·분담 규칙이 필요하다. Seat SDK·좌석 권한·사람↔좌석 연결은 MVP 구현·시연·완료 조건에서 제외한다.

| 우선순위 | 기능 | 완료 기준 |
| --- | --- | --- |
| P0 | 동행 생성 | 분담 방식, 비용 모델, 운전자를 설정하고 동행 ID를 만든다. |
| P0 | 동승자 등록·개인 페이지 연결 | 차량에서 명단을 만들거나 휴대폰 QR로 참여하고 실제 탑승을 확인한다. 개인 페이지 연결은 하차 전에도 가능하다. |
| P0 | 차량 거리 취득 | 출발·탑승자 변경·도착 시 SDK 누적거리를 읽고 저장한다. |
| P0 | 시간–누적거리 이력 | 동행 중 거리 업데이트와 검증한 주기의 조회값을 시각과 함께 저장한다. 주차 상태 전환도 기록하며 조회 공백을 구분한다. 화면을 계속 갱신할 필요는 없다. |
| P0 | 사람별 ‘내려요’·구간 확정 | 주차 중 각 동승자의 버튼으로 현재 거리까지 기록한다. 센서의 빈 좌석 판정·실제 하차·전체 운행 종료를 기다리지 않는다. |
| P0 | 탑승 구간 확인·사후 수정 | 시간·주차 기록을 선택해 탑승 시작·종료 구간을 수정하고 영향받는 사람들의 금액을 재계산한다. 추정·수동 보정·변경 이력·공유 후 차액을 표시한다. |
| P0 | 구간별 비용 계산 | 거리와 사전 합의한 비용 모델로 개인별 금액과 근거를 제시한다. |
| P0 | 모바일 정산표 | 각자 이용한 구간, 비용 구성, 운전자에게 보낼 금액을 확인한다. |
| P0 | 정산 수단 선택·외부 송금 연결 | 카카오페이·토스 계열 중 검증된 수단을 선택하고 수취 링크와 금액 복사를 제공한다. 링크가 없으면 수동 송금 안내를 제공한다. |
| P0 | 저장·복구·주행 제한 | 재실행 시 진행 중 동행을 복원하고 차량의 제한 상태에 맞게 조작을 잠근다. |
| P1 | 톨비·주차비 수동 입력 | 비용이 적용될 구간 또는 대상자를 지정해 추가한다. |
| P1 | 차량 연비 연동 | 지원 여부와 단위를 검증한 뒤 추정 유류비에 반영한다. |
| P1 · 도어·위치 연동 검증 후 | 정차·도어 기반 하차 후보 | 정차 때 시간·누적거리를 저장하고 도어 개폐 시 위치를 짧게 수집해 후보를 보강한다. 사용자가 후보를 선택해야 구간 수정에 반영한다. 도어 미지원·위치 실패 시 시간 선택 유지 |
| P1 · 위치 연동 검증 후 | 장소·지도 기반 구간 수정 | 정차·도어 후보에 저장한 위치–시간–누적거리를 선택한 장소와 연결한다. 같은 장소 재방문은 시각별 후보로 구분하며 기록이 없으면 시간 선택으로 안내한다. |
| P1 | 정산 화면 광고·캐릭터 연출 | 정산표 옆 광고와 확정 주행거리 누적 애니메이션에 스폰서 캐릭터를 적용한다. 공모전은 광고 목업으로 시연한다. |
| 후속 · 이용자 정착 후 | 건당 정산 수수료 | 정산금 일부를 플랫폼에 귀속한다. 예시 100원의 과금 단위·부담 주체·분리 지급 구조를 확정한 뒤 도입한다. |
| 후속 · 선택 | 좌석 정합성 안내·재미 요소 | 유효한 점유값이 있을 때 등록 명단과의 차이를 주차 중 확인하도록 돕거나 캐릭터 반응에 활용한다. 자동 인원·구간·금액 변경 없이 진행하며 MVP 완료를 막지 않는다. |
| 후속 | 경유지 표시, 전기차 비용 모델 | 별도 지원 검증 후 확장한다. |

MVP는 자동 출금, 송금 완료 자동 판정, 톨비 자동 수집, 좌석 센서만으로 개인 식별, 낯선 사람 간 카풀 매칭을 구현 범위에 넣지 않는다. 현재 구현 기본안은 운전자가 공동 비용을 먼저 지불하고 동승자가 운전자에게 보내는 모델이다. MVP의 플랫폼 수수료는 0원이며, 유료화는 §12의 단계별 모델로 도입한다. 다수 결제자의 상호 채무 상계는 후속 과제다.

## 4. 차량 정보와 SDK 사용 기준

### 공식 문서로 확인한 범위

| 정보 | 공식 문서의 근거 | 제품에서의 역할 | 실제 환경에서 확인할 것 |
| --- | --- | --- | --- |
| 누적 주행거리 | Odometer, `getCurrentDistanceDriven()` · 공식 명세는 `Float?`, km | 구간 거리 산정의 필수 입력 | 차량별 지원·실제 정밀도, Capability, 실패와 재연결 |
| 좌석 점유 · 후속 선택 | Seat, `getCurrentSeatOccupancy(area)` · `Boolean?` | 등록 명단의 정합성 확인 안내·캐릭터 반응. 구간·정산 계산에는 사용하지 않음 | 좌석별 지원·누락, 운전자 포함 등 비교 대상 일치, 짐·좌석 이동의 영향 |
| 도어 개폐 · 선택 | Door, `checkDoorPositionCapabilities()`·`getCurrentDoorPosition()`·`registerDoorPosition()` | 정차 중 하차 후보 기록의 계기. 특정인의 하차를 확정하지 않음 | 영역별 지원·값 범위·실제 알림 수신·초기 상태·중복 이벤트 |
| 연비 | Fuel의 `getCurrentFuelEconomy()`·`getCumulativeFuelEconomy()` · `Float?`, L/100km | 추정 비용 모델의 선택 입력 | 운행 세션·누적 기간과 동행 구간의 일치 여부, 값의 유효성·차량별 지원 |
| 위치·경로 · 선택 | FusedLocation, NaviHelper | 정차·도어 후보의 위치 스냅샷, 장소 기반 구간 수정·구간명 표시 | 지원·권한·짧은 구독·해제, 위치의 시각·신뢰도·신선도, 거리 기록과의 시각 정합성 |
| 통행료 관련 | Toll 도메인은 ETCS 안내 음량 등을 다룬다. | MVP는 통행료 수동 입력 | 실제 결제 금액 조회는 확인되지 않았으므로 자동 수집을 약속하지 않는다. |

근거: [Vehicle SDK 소개][pleos-vehicle], [Odometer API][pleos-odometer], [Seat API][pleos-seat]. API 문서의 존재가 모든 차량에서의 지원을 보장하지는 않는다. 상세 함수 서명과 반환 단위는 사용할 SDK에서 다시 확인한다.

2026-11-03에 확인한 Seat 명세는 좌석 영역별 **점유 여부 `Boolean?`**를 제공한다. 이를 압력·체중 원시값이나 개인 식별 결과로 표현하지 않는다. 후속 기능에서 특정 사람의 좌석 상태를 보여주려면 별도로 확인한 사람↔좌석 연결이 필요하지만, 전체 인원 비교에는 그 연결을 필수로 요구하지 않는다. 최종 탑승 구간은 확인된 명단과 사람별 하차 확정 기록을 기준으로 한다. [Seat API][pleos-seat]

2026-11-03에 확인한 공식 Vehicle SDK Sample App은 도어 영역별 지원 조회·현재 위치 조회·변경 알림 구독·해제를 제공한다. 관련 함수는 `checkDoorPositionCapabilities()`, `getCurrentDoorPosition()`, `registerDoorPosition()`, `unregisterDoorPosition()`이다. 예제의 0..1 범위를 모든 환경에 고정 적용하지 않고 실제 영역별 지원과 값을 확인한다. 도어 잠금 상태를 개폐 상태로 대신 사용하지 않는다. [Door API 목록][pleos-door], [공식 도어 예제][pleos-door-sample]

2026-11-02에 공식 상세 명세를 확인한 Fuel 항목은 다음과 같다. `getCurrentFuelEconomy()`는 현재 운행 세션, `getCumulativeFuelEconomy()`는 차량의 누적 운행 기간에 대한 연비이며 단위는 모두 **L/100km**다. `getInstantaneousFuelEconomy()`는 순간 연비이고, `getFuelPercent()`는 `Int?` 형태의 잔량 비율(%)이다. [현재 연비][pleos-fuel-current], [누적 연비][pleos-fuel-cumulative], [순간 연비][pleos-fuel-instant], [잔량 비율][pleos-fuel-percent]

확인한 공개 Fuel 목록에서는 **이번 동행·임의 구간의 소비 연료량(L), 유가(원/L), 실제 주유 결제 내역**을 직접 반환하는 API는 찾지 못했다. 따라서 이 정보까지 SDK가 자동 제공한다고 설명하지 않는다. 연비 측정 기간이 동행과 다를 수 있고 잔량 비율은 소비량 계량값과 다르므로, 현재 설계에서는 유류비를 추정값으로 제공한다. [Fuel API 목록][pleos-fuel]

2026-11-03 공개 문서에는 Odometer의 `registerDistanceDriven()`과 차량 상태 변경을 구독하는 방식이 안내되어 있다. 이를 앱에서 시각과 함께 저장하는 **시간–누적거리 이력**을 설계한다. 공개 API 목록·구독 방식 확인과 실제 업데이트 주기·정밀도·주행 중 수집 검증은 구분한다. 과거 이력이 SDK에서 자동 조회된다고 가정하지 않는다. [거리 구독 API][pleos-odometer-subscribe], [차량 상태 구독 가이드][pleos-callback]

FusedLocation v1.1.3의 공개 문서는 위치 업데이트 수신과 위도·경도·타임스탬프 등을 설명한다. `getLastKnownLocation()`은 새 위치를 계산하지 않으며 마지막 값 또는 null을 반환할 수 있다. 한편 프로젝트·SDK 신청 가이드는 FusedLocation을 준비 중으로 안내하므로 실제 포털 상태·`isSupported()`·권한·업데이트 수신을 확인해야 한다. **위치 SDK 사용은 P0의 전제 조건으로 두지 않는다.** NaviHelper도 현재 위치 정보 콜백을 제공하지만 전달 이벤트가 Navigation 앱의 상태에 따라 달라질 수 있으므로 자동 대체 가능하다고 가정하지 않는다. [FusedLocation 소개][pleos-location], [위치 데이터 접근][pleos-location-access], [프로젝트 생성 및 SDK 사용 신청][pleos-project], [NaviHelper 이벤트][pleos-navi-events]

### 연결과 권한

- Vehicle 연결을 초기화한 뒤 도메인 객체를 얻는다. Capability와 조회 결과는 `onComplete` / `onFailed`로 비동기 처리한다. 완료 전에 연결을 해제하지 않는다. [Vehicle SDK 소개][pleos-vehicle]
- MVP의 거리 조회에는 Odometer의 `pleos.car.permission.CAR_DRIVE`를 사용한다. 후속 Seat 연동 시 `pleos.car.permission.CAR_SEATS`, 차량 Fuel 연동 시 `pleos.car.permission.CAR_ENERGY`를 해당 기능에 맞춰 추가한다. 사용하는 함수의 `@RequiresPermission`을 확인하며 MVP에 Seat 권한을 요구하지 않는다. [권한 가이드][pleos-permissions]
- 장소 기반 수정에 FusedLocation을 사용하면 `pleos.car.permission.FUSED_LOCATION` 권한과 지원 환경을 별도로 확인한다. 시간 기반 수정은 위치 권한 없이 구성한다. [FusedLocation 소개][pleos-location]
- 선택 도어 조회·구독에는 `pleos.car.permission.CAR_DOORS`를 사용한다. 도어를 작동시키는 제어 권한은 필요하지 않다. 영역별 Capability와 실제 알림 수신을 검증하고 등록했던 리스너·영역으로 해제한다. [공식 도어 예제][pleos-door-sample]
- 차량 상태 조회만으로 MVP를 구성한다. 좌석·도어·공조 같은 차량 제어 권한은 필요하지 않다.
- SDK 어댑터에서 거리를 하나의 내부 단위로 정규화한다. Console의 km 표기를 SDK 원시값의 단위로 간주하지 않는다.
- 거리 조회 실패는 0km가 아니다. 경계 확정을 보류하고 재시도 또는 명시적인 수동 보정으로 처리한다.
- 수동 보정값과 테스트 입력은 출처를 표시한다. 실제 SDK 데이터와 모의 데이터를 바꿔 보여주지 않는다.

## 5. 사용자 흐름과 주행 중 동작

### 기본 흐름

1. **주차 상태에서 동행 생성:** 운전자가 비용 모델과 운전자 포함 여부를 설정한다.
2. **명단·개인 페이지 연결:** 차량에서 동승자를 추가하거나 QR로 별칭 등록을 받는다. 주차 중 명단을 확인하고, 연결한 동승자는 개인 페이지 주소를 보관한다. QR은 하차 전부터 열 수 있다.
3. **출발 확정:** 실제 탑승한 명단을 확인하고 SDK에서 누적거리를 읽어 첫 구간의 탑승자를 저장한다. 좌석 지정은 필요하지 않다.
4. **이동:** 별도 화면 조작 없이 이동한다. 누락 하차의 사후 수정을 위해 시간–누적거리 이력을 로컬에 저장한다. 연속 GPS 수집이나 실시간 화면 갱신은 MVP에 필요하지 않다.
5. **중간 하차 예정:** 주차 상태에서 차량 화면의 `[A 내려요]`를 누른다. 현재 누적거리 조회 성공 후 이전 구간과 A의 이번 탑승을 닫고 남은 D·B로 다음 구간을 시작한다. A는 아직 차 안에서 정산 페이지·개인 QR을 확인할 수 있다.
6. **동행 종료:** 마지막 누적거리와 추가 비용을 확인해 정산표를 만든다.
7. **정산 공유:** 하차한 사람은 나머지 동행이 계속되는 중에도 개인 페이지를 열 수 있다. 현재 구간 기준 잠정 금액과 비용 검토 후 확정 금액을 구분하고, 확정한 금액으로 카카오페이·토스 중 사용 가능한 송금 수단을 선택한다.
8. **수취 확인:** 운전자가 외부 앱에서 입금을 확인한 뒤 탄만큼에서 수취 확인을 기록한다.

같은 시점에 여러 사람이 타거나 내리면 하나의 거리 스냅샷으로 기존 구간을 닫고 새 명단을 적용한다. 중간 합류와 재탑승도 같은 방식으로 처리한다.

### 사람별 하차 버튼 · QR·센서와의 역할 분담

하차 버튼은 **하차할 의사를 미리 표시하고 현재 위치까지의 탑승 기록을 확정**하는 조작이다. 사람이 실제로 차 밖에 나가거나 센서가 Empty가 되어야 누를 수 있는 구조로 만들지 않는다.

| 요소 | 맡는 역할 |
| --- | --- |
| QR·개인 링크 | 출발 전·주차 중 등록, 개인 페이지 접근·공유. 하차 확정 전에는 진행 중 예상 내역도 확인 가능 |
| Odometer | 출발·탑승자 변경·종료 경계의 실제 누적거리 조회 |
| 좌석 점유 · 후속 선택 | 명단 확인 안내·재미 요소에만 활용. 구간 확정과 금액 계산에 영향 없음 |
| 사람별 `[A 내려요]` / `[B 내려요]` | 주차 중 선택한 사람의 탑승 종료를 확정하고 해당 사람의 정산 페이지·QR 안내 |
| 비용 검토·송금 | 구간 확정 후 비용·추가 비용을 확인해 금액을 확정. 실제 하차 여부·센서 상태와 독립 |

차량 화면에는 별칭과 탑승 상태를 붙인 개별 버튼을 둔다. 누르면 ‘하차 처리 중’으로 중복 입력을 막고, 거리 조회 성공 후 ‘하차 완료 · 10km’와 개인 페이지 안내를 표시한다. 거리 조회 실패 시 금액을 확정하지 않고 재시도·검토로 연결한다. 주행 제한이 활성화된 차량 화면에서는 조작을 막는다.

주차 중 잘못 누른 경우에는 취소·수정할 수 있게 하고, 이미 이동·공유·송금이 진행됐으면 구간·정산 버전 수정 절차를 따른다. 재탑승은 새 탑승 기록으로 처리한다. 잠깐 자리에서 일어나거나 휴게소에서 내린 것만으로 자동 정산하지 않으며, 하차 버튼 직후 QR을 확인하려고 계속 앉아 있는 동안에도 확정 기록을 자동 취소하지 않는다.

하차 확인은 개인 탑승 기록을 닫는 것이며 동행 전체 종료와 별개다. 개인 구간이 닫히면 Trip이 ACTIVE여도 개인 정산 페이지를 제공한다. 뒤늦게 추가 비용을 입력할 수 있는 상태라면 ‘잠정 금액’을 표시하고 개인별 비용 검토를 거쳐 확정한다. 전체 동행이 끝나야 QR을 발급하거나 페이지를 열 수 있다는 조건을 두지 않는다.

### ‘내려요’를 깜빡한 경우 · 탑승 구간 사후 수정

**탑승 구간 수정은 MVP 필수 기능으로 두고, 사용자에게 시간·주차 기록을 먼저 고르게 한다.** 하차 버튼 누락을 발견했다고 현재 누적거리로 과거 하차를 처리하지 않는다. 앱이 동행 중 시간–누적거리 이력을 미리 저장해야 선택한 시각을 당시의 거리와 연결할 수 있다. 기록하지 못한 과거 구간은 뒤늦은 조회만으로 정확히 복원할 수 없다.

1. **기록 확인:** 동행 종료·정산 확정 전 사람별 탑승 구간과 거리를 보여주고 ‘중간에 먼저 내린 분이 있나요?’를 확인한다. 진행 중·종료 후에도 ‘탑승 구간 수정’을 제공한다.
2. **수정 요청:** 동승자는 연결된 개인 페이지에서 자신의 탑승 시작·종료 구간 수정을 요청한다. 운전자는 주차 중 차량 화면에서 확인·반영한다. 개인 페이지 연결이 없어도 운전자가 해당 사람과 확인해 수정할 수 있다. 동승자가 다른 사람의 기록을 직접 바꾸지는 않는다.
3. **시간·주차 기록 선택:** ‘언제 내리셨나요?’에서 대략적인 시각이나 주차 상태 전환 기록을 선택한다. 앱이 가까운 유효한 시간–누적거리 기록과 기록 간격을 보여주고 하차 거리 후보를 계산한다. 위치 연동을 검증한 환경에서는 장소·지도 선택도 제공한다. 기록 공백이 있거나 값을 정하지 못하면 검토 중으로 남기고, 합의한 거리 수동 보정은 보조 수단으로 제공한다.
4. **변경 미리보기:** 수정 전후의 구간·거리와 영향받는 모든 사람의 부담액·차액을 함께 보여준다. 수정한 사람의 금액만 바꾸지 않고 구간별 분담 인원과 관련 비용 배분을 다시 계산한다.
5. **확인·반영:** 운전자가 수정 사유와 근거를 확인해 반영한다. 원래 SDK 관측값은 보존하고 수정자·확인자·수정 시각·이전/이후 경계·입력 출처를 남긴다. 영향받는 사람의 개인 페이지에도 변경 사유와 최신 정산 버전을 표시한다.

예를 들어 §6의 20km 동행에서 A의 하차를 누락해 D·A·B가 모두 20km를 탄 것으로 기록하면 각 1,000원이다. A의 종료 지점을 10km로 수정하면 D 1,250원 / A 500원 / B 1,250원이 된다. 총 3,000원은 같고 세 사람의 부담액이 함께 바뀐다. 10km가 기억에 따른 입력이면 영수증에도 수동 보정·추정임을 표시한다.

수정 경계는 해당 동행의 관측된 거리 범위 안에 있어야 하며 시작≤종료, 동일인의 재탑승 기록 간 중복 없음 등을 확인한다. 잘못 선택한 종료 경계를 취소하거나 별도 재탑승 회차를 수정할 수 있어야 한다. ACTIVE 동행의 과거 구간 수정은 현재 진행 중인 동행을 종료하지 않는다.

공유 전에는 변경 내역을 확인한 뒤 정산을 확정한다. 공유 후에는 새 정산 버전을 검토·확정하고 이전 페이지에는 변경 상태를 표시한다. 검토 중인 정산에서는 이전 금액으로 새 송금을 안내하지 않는다. 이미 보냈거나 수취 확인된 내역은 보존하고, 변경된 부담액과 기존 송금·수취 상태를 대조해 추가 송금 또는 돌려줄 금액을 안내한다. ‘보냈어요’만으로 입금을 확정하거나 차액을 자동 출금·환불하지 않는다.

### 시간·장소를 거리 기록과 연결하는 방법

| 사용자 입력 | 필요한 저장 기록 | 구간 수정 방식 |
| --- | --- | --- |
| ‘오후 2시 30분쯤 내렸어요’ · MVP | 동행 중 시각–누적거리 이력 | 선택한 시각 근처의 유효 기록을 찾아 거리 후보와 기록 범위를 제시 |
| ‘이때 잠깐 주차했을 때 내렸어요’ · MVP | 주차 상태 전환 시각·누적거리 | 주차 기록을 후보로 제공. 주차 자체를 개인 하차로 자동 확정하지 않음 |
| ‘문을 열었던 이 지점에서 내렸어요’ · 도어 연동 후 | 정차·도어 이벤트 시각·누적거리, 가능한 경우 위치 스냅샷 | 실제 이벤트를 후보로 제공하고 사용자가 본인의 하차 지점으로 선택 |
| ‘이 역 근처에서 내렸어요’ · 위치 연동 후 | 정차·도어 후보의 위치–시각–누적거리, 장소 검색·지도 | 저장한 후보 중 장소와 가까운 기록을 시각과 함께 제시. 같은 장소 재방문 시 사용자가 선택 |

**시간은 과거 거리 기록을 찾는 열쇠이며, 분담 기준은 계속 실제 주행거리다.** 전체 운행 시간의 비율로 거리를 나누거나, 지도에서 출발지→하차 장소의 최단거리를 새로 계산해 실제 차량 이용 거리로 취급하지 않는다. 장소 검색·주소 변환은 별도 지도 서비스 연동이 필요하며 FusedLocation이 장소명·과거 이동 이력까지 자동 제공한다고 설명하지 않는다.

구현 기본안은 동행 ACTIVE 동안 거리 변경 구독을 받고, 검증한 주기의 조회 및 출발·주차 전환·하차·종료 스냅샷을 보완 저장하는 것이다. 5~10초 조회는 초기 실험 후보이며 SDK의 보장 주기가 아니다. 앱 수신 시각과 단조 시간·수집 세션, 유효성·실패 공백을 함께 남기고 SDK 측 관측 시각이 제공되면 별도로 보존한다. 수신 시각을 실제 차량 측정 시각과 동일하다고 단정하지 않는다.

시간 선택에 따른 근접값·기록 사이 보간은 ‘기록 기반 추정’으로 표시한다. 큰 수집 공백·재연결·시계 변경을 가로질러 자동 보간하지 않으며, 오래된 위치를 현재 거리와 묶지 않는다. 추정 범위와 기록 정밀도를 확인한 뒤 운전자가 반영한다. 이력의 각 점은 정산 구간을 만들지 않으며, 확인된 수정 경계만 구간 분할·금액 계산에 사용한다.

장소 기반 수정은 실제 지원·권한과 위치 수신이 검증된 경우에만 제공한다. 우선 정차·도어 이벤트의 지점만 저장하는 방식으로 설계하며 연속 위치 경로 저장은 별도로 검토한다. 위치 미지원·차단·오차·기록 공백에서는 시간 선택으로 안내한다. 위치와 누적거리의 수집 시각을 맞추고 신뢰할 수 있는 실제 방문 후보만 제시한다. 기록된 방문이 없으면 장소명만으로 과거 하차 거리를 확정하지 않는다.

### 선택 기능 · 정차·도어 이벤트 때 위치 스냅샷

**정차 지점에서 필요한 위치만 짧게 수집하고, 도어 개폐를 하차 후보의 계기로 사용한다.** 시간–누적거리 이력은 유지하며 도어·위치 연동이 가능한 환경에서 후보 선택을 더 쉽게 만든다. 정차 판정에 사용할 차량 상태·차속 신호와 단위·지연은 실제 환경에서 검증한다. 속도 0인 정차와 플랫폼이 허용하는 주차 중 화면 조작은 구분한다.

1. **정차 후보 생성:** 동행 ACTIVE 중 정차를 확인하면 당시 시각과 누적거리를 남긴다. 검증한 지속 시간·중복 억제 기준으로 짧은 신호 대기·반복 정차가 목록을 가득 채우지 않게 한다.
2. **도어 이벤트 연결:** 같은 정차 중 도어 열림·닫힘 알림을 해당 후보에 연결하고 어느 영역의 문인지 저장한다. 문이 열린 후보를 우선 제시한다. 초기 상태 조회나 재연결 직후 이미 열린 문을 새 하차 이벤트로 단정하지 않는다.
3. **짧은 위치 수집:** 후보 생성·도어 열림 시 `getLastKnownLocation()`으로 얻은 값의 시각·신뢰도를 확인한다. 오래됐거나 null이면 짧은 제한 시간 동안 `registerFusedLocationCallback()`으로 업데이트를 기다리고 성공·제한 시간 종료·이동 재개 시 구독을 해제한다. 새 위치가 반드시 도착한다고 가정하지 않는다. [위치 데이터 접근][pleos-location-access]
4. **후보 보관:** 위치가 해당 정차 시점과 맞으면 시각·누적거리와 함께 저장한다. 다음 이동 지점에서 도착한 위치를 이전 정차에 붙이지 않는다. 위치 실패 시에도 시간·누적거리 후보는 유지하고 ‘위치 확인 불가’로 표시한다. 동일 정차의 문 반복 개폐·여러 문 이벤트는 하나의 후보에 묶는다.
5. **사용자 확인:** 개인 페이지에서 ‘14:32 · 정차 지점 · 오른쪽 뒷문 열림’ 같은 기록을 보여주고 ‘여기서 내렸어요’를 선택받는다. 지원되는 영역과 위치명이 확인된 경우에만 해당 표현을 사용한다. 차량 화면의 확인·구간 수정은 주차 중에 제공한다.

문은 짐을 꺼내려고 열 수도 있고 여러 사람이 같은 문을 쓸 수도 있다. 이벤트만으로 특정 사람을 식별하거나 하차·재탑승·분담 인원·금액을 변경하지 않는다. 하차 버튼, 시간 선택, 도어 후보 선택은 모두 같은 구간 수정·확인 절차로 연결한다. 도어 미지원·이벤트 누락 시에도 기존 시간 선택을 유지한다. 도어·위치 기능은 MVP 완료의 필수 조건으로 두지 않는다.

### 후속 선택 · 좌석 정합성 안내와 재미 요소

Seat 연동은 MVP를 완성한 뒤 별도로 검토한다. **등록은 했지만 실제로 타지 않은 사람을 발견하도록 돕는 확인 신호**로 사용할 수 있다. 예를 들어 운전자 포함 3명이 탑승 중으로 등록되어 있는데 비교 대상 좌석의 유효한 점유값이 2자리라면, 주차 중 ‘등록은 3명, 감지된 점유는 2자리예요. 명단을 확인해 주세요’라고 비차단 안내한다. 사용자가 실제 탑승 여부를 확인하고 명단을 수정할 때만 구간 기록에 반영한다.

비교는 운전자 포함 여부와 좌석 범위를 맞추고, 필요한 좌석이 지원되며 유효한 값을 받았을 때만 한다. 미지원·null·조회 지연은 ‘확인 불가’로 표시한다. 점유 개수가 같아도 짐이 섞였을 수 있으므로 ‘전원 탑승 확인’으로 확정하지 않는다. 차이가 있어도 누가 안 탔는지 자동 판별·제외하거나 출발·정산을 막지 않는다.

재미 요소는 주차 중 좌석 점유에 따라 캐릭터가 인사하거나 표정을 바꾸는 정도로 검토한다. 탑승 인증·분담 인원·요금 산정과 연결하지 않으며 주행 제한과 동작 줄이기 정책을 따른다.

### 좌석 보조 도입 시 · 짐을 사람으로 계산하지 않는 원칙

**분담 인원은 확인된 사람 명단으로만 계산한다.** 좌석 점유 신호만으로 Participant·RideSession·SeatBinding을 만들거나 재활성화하지 않는다. 무거운 짐 때문에 Occupied 신호가 발생하더라도 명단·분담 인원·정산 금액은 그대로 유지한다. SDK가 사람과 물체를 구별한다고 가정하지 않는다.

| 상황 | 처리 기준 |
| --- | --- |
| 사람과 연결하지 않은 좌석이 Occupied | ‘사람 미연결 좌석 점유’ 보조 정보로만 처리. 필요 시 주차 중 확인 안내를 제공하되, 정산 진행을 막거나 사람을 자동 추가하지 않음 |
| 짐을 올리거나 다른 좌석으로 옮김·제거 | 확인된 명단·탑승 구간·개인 금액 변경 없음 |
| 등록된 사람이 내린 자리에 짐을 놓음 | 하차 확정 기록을 유지. 해당 사람을 자동 재탑승 처리하지 않음 |
| 등록된 사람의 좌석 신호가 Empty·null·미지원 | 사람을 자동 하차·제외하지 않음. 사람별 버튼·확인 기록을 유지 |

센서 이벤트는 탑승 구간을 만들거나 확정된 경계를 덮어쓰지 않는다. 센서 보조를 켜거나 끄거나 짐에 의한 점유 이벤트를 추가해도 **같은 명단·확정 경계·비용 입력이면 정산 결과가 같아야 한다.**

### 출발 전 정산 규칙 · 설명 모션그래픽

사용자 지정 방향은 정산 규칙을 화면의 모션그래픽으로 설명하는 것이다. **함께 탄 구간은 함께 나누고, 내린 뒤 구간은 남은 사람이 나눈다**는 원리를 약 10초의 예시로 보여준다. 동일한 캐릭터를 안내자로 사용할 수 있다.

| 시간 · 구성 기본안 | 움직임 | 화면에서 이해할 규칙 |
| --- | --- | --- |
| 0–2초 | 운전자 D와 동승자 A·B가 차량에 합류 | 이번 예시는 운전자 포함, 세 명이 분담 |
| 2–4초 | 차량이 첫 10km 구간을 이동하고 비용이 세 사람에게 배분 | 1,500원을 세 명이 나눠 각 500원 |
| 4–6초 | A가 중간 지점에서 내려 정지하고 차량에는 D·B가 남음 | A는 여기까지 탄 구간만 부담 |
| 6–8초 | 차량이 다음 10km 구간을 이동하고 D·B에게만 비용이 배분 | 다음 1,500원은 두 명이 나눠 각 750원 |
| 8–10초 | 최종 부담액과 이번 동행의 실제 설정을 정지 화면으로 표시 | 예시 D 1,250원 / A 500원 / B 1,250원, 이어서 현재 규칙 확인 |

예시 금액은 §6과 같은 연비·유가의 가상 데이터다. 설명 장면에는 ‘예시’를 표시하고 실제 동행 금액과 구분한다. 운전자 제외로 설정하면 분담 대상과 예시 결과도 일치시킨다. 예시 뒤에는 이번 동행의 운전자 포함 여부·연비·유가·추가 비용 원칙을 확인할 수 있게 한다.

차량에서는 주차 상태, 동승자는 QR 참여 후 모바일에서 볼 수 있다. 처음에는 설명을 제공하고 이후에는 요약과 ‘다시 보기’를 기본으로 한다. 재생 중에도 건너뛰고 규칙을 확인할 수 있으며, 영상 시청을 동의 기록으로 취급하지 않는다. 규칙을 바꾸면 최신 요약을 바로 표시하고 재생을 반복 강제하지 않는다.

움직임은 차량·탑승자·비용 배분의 관계를 설명하는 데 사용한다. 읽는 금액은 구간 확정 장면에서 정지시킨다. 주행 제한 전환 시 재생을 중단하고, 동작 줄이기 환경에서는 구간별 정지 그림과 최종 규칙을 제공한다. 상용 화면의 모션 시간은 사용성 확인 후 조정하며, 현재는 기획과 검토용 예시다.

### 차량 앱의 뷰포트와 동승자 모바일

공식 자료 확인 결과, 차량 패널 전체와 탄만큼에 배정되는 앱 창은 다르다. Driving view는 고정 영역이고 앱 영역에는 최대 두 앱이 표시된다. 따라서 차량용은 **넓은 확장 창과 다른 앱 옆의 좁은 창**을 모두 설계한다. [앱 구조 및 동작 모델][pleos-window-model], [디스플레이 구성][pleos-display-layout]

| 공식 창 정책 | 확인 내용 |
| --- | --- |
| Connect-S | 앱 1개는 2:0 확장, 앱 2개는 1:1 분할. 두 앱의 창은 일반적으로 portrait 형태다. |
| Connect-W | 2:1 또는 1:2 분할을 제공하므로 두 앱을 표시해도 넓은 쪽은 가로형일 수 있다. |
| 창 변경 | 사용자가 창 위치·크기를 바꿀 수 있다. 실제 배정 영역에 맞춰 화면을 다시 구성하고 진행 중 동행 상태를 유지한다. |

정책 근거: [Window Policy][pleos-window-policy]. 설계 기준은 음악의 재생 여부가 아니라 **현재 탄만큼 앱 창의 크기**다. 음악 앱과 탄만큼을 함께 표시하는 상태도 검증한다. 앱의 확장 화면은 Driving view·상태 표시줄·GNB까지 차지하는 차량 전체 화면을 의미하지 않는다.

공식 폼 팩터 테스트 가이드의 화면에는 다음 가상 앱 화면 예시가 있다. **테스트 프리셋의 예시이며 모든 양산 차량의 고정 뷰포트 규격으로 간주하지 않는다.** 패널 해상도(px), 밀도(DPI), 앱 레이아웃 단위(dp)를 구분하고 실제 앱 창·시스템 영역·인셋을 측정한다. [폼 팩터 테스트 가이드][pleos-form-factor]

| 가이드의 가상 화면 예시 | 표시된 앱 테스트 크기 |
| --- | --- |
| Connect-S 12.9인치 · Portrait | 628 × 855dp |
| Connect-S 14.6인치 · Landscape | 1360 × 948dp |
| Connect-S 17인치 · Portrait | 840 × 1184dp |

탄만큼의 화면 역할은 다음처럼 나눈다. 좁은 차량 창을 휴대폰 화면과 같은 크기·입력 조건으로 취급하지 않는다.

| 화면 | 구성 기본안 |
| --- | --- |
| 차량 · 넓은 창 | 왼쪽에 구간·탑승자, 오른쪽에 분담 요약·정산 공유 QR. 설명 모션그래픽도 가로 공간에 맞춰 재배치 |
| 차량 · 좁은 창 | 동행 상태·탑승자·핵심 확인 버튼을 우선하고 상세 계산은 필요 시 펼침. 음악 앱과 병행해도 주요 조작 유지 |
| 동승자 · 모바일 웹 | QR 참여, 개인 영수증, 카카오페이·토스 송금 선택. 기존 동행 티켓·여정 노트 시안은 이 화면의 검토안 |

### 주행 제한

Pleos는 플랫폼의 `CarUxRestrictions`에 따라 UX 제한을 반영하도록 안내한다. DO를 선언하지 않은 앱은 기본적으로 주행 중 사용이 제한된다. [주행 규제 개발 가이드][pleos-driving], [지역별 정책][pleos-driving-policy]

구현 기본안은 동행 설정, QR 표시, 탑승자 수정, 정산 확인을 주차 중에 제공하는 것이다. 속도 0만으로 주차 상태를 판정하지 않는다. 플랫폼 제한이 활성화되면 진행 중 조작을 중단하고 저장된 상태를 유지한다. 제한 상태를 확인할 수 없을 때는 조작을 잠근다.

주행 중 앱 화면이나 프로세스가 계속 실행된다고 가정하지 않는다. 다음 주차 시 누적거리와 저장된 동행을 다시 읽어 이어간다. 제한 상태에서의 실제 프로세스·콜백 동작은 에뮬레이터 검증 항목이다.

광고와 캐릭터·주행거리 애니메이션은 차량의 주차 중 정산 화면과 동승자의 모바일 정산 화면에 배치한다. 차량에서 주행 제한이 활성화되면 광고·장식 애니메이션을 중단한다. 이는 주행 중 움직이는 이미지·반복 애니메이션을 최소화하거나 제한하도록 안내하는 공식 설계 원칙을 반영한 구현 기준이다. [주행 안전을 고려한 설계][pleos-driving-safety]

## 6. 비용 계산 규칙

### 구현 기본안

- 기본 분담은 **운전자 포함, 각 구간 탑승자 균등 분담**이다.
- 운전자 제외도 동행 생성 시 선택할 수 있게 하되, 모든 참여자에게 적용 방식을 보여준다.
- 사전에 합의한 규칙을 동행에 저장한다. 변경 시 전체를 재계산하고 정산 버전을 올린다.
- 운전자만 이동하는 구간은 운전자 부담으로 기록한다. 운전자 제외 모드에서도 다른 구간의 동승자에게 넘기지 않는다.
- 연비·유가 수동 입력을 P0 기본 모델로 삼는다. 차량 연비가 검증되면 입력 출처를 바꿀 수 있다.
- 내연기관 기준 모델을 먼저 구현한다. 전기차에서 연료 모델을 자동 적용하지 않는다.

### 수식

```text
구간 거리(km) = 종료 누적거리(km) - 시작 누적거리(km)
추정 유류비(원) = 구간 거리(km) / 연비(km/L) × 유가(원/L)
구간 비용(원) = 추정 유류비 + 해당 구간에 배정한 추가 비용
개인 부담액(원) = 본인이 분담 대상인 각 구간의 배분액 합계
동승자의 송금액(원) = 해당 동승자의 개인 부담액
```

위 연비 수식은 사용자 입력을 km/L로 받는 경우다. SDK의 L/100km 값을 사용하면 다음처럼 계산한다. 두 단위를 혼용하지 않는다.

```text
추정 유류비(원) = 구간 거리(km) × 연비(L/100km) / 100 × 유가(원/L)
연비(km/L) = 100 / 연비(L/100km)  // 유효한 양수 값일 때
```

추정에 필요한 최소 입력은 거리·적용할 연비·유가다. 거리는 SDK에서 읽고, 연비는 검증된 SDK 값 또는 운전자가 확인한 기준값, 유가는 수동 입력을 기본으로 한다. 유종·단가·기준일·출처를 기록하고 동행의 적용 기준을 공유한다. 외부 유가 정보 연동은 별도 검증 후 추가한다.

정차 시 읽은 순간 연비를 전체 구간에 적용하거나, 누적 연비의 전후 차이를 소비 연료량으로 쓰지 않는다. 잔량 %의 차이로 소비량을 추정하려면 탱크 용량·측정 정밀도·중간 주유 여부 등이 추가로 필요하므로 MVP 정산 근거로 사용하지 않는다. 주유 영수증의 구매량·결제액도 이번 동행의 소비량·비용과 자동으로 같아지는 것은 아니다. 구간 소비량을 실측한 것처럼 ‘정확한 실지출 자동 계산’으로 표현하지 않는다.

운전자의 개인 부담액은 비용 분담을 설명하는 값이며, 운전자 자신에게 보낼 송금액을 만들지 않는다. 유류비는 **추정**, 직접 입력한 톨비·주차비는 **입력 비용**으로 표시한다. 순간 연비나 연료 게이지 변화만으로 실제 지출을 확정하지 않는다.

추가 비용은 입력 단계에서 적용 구간 또는 대상자를 정한다. 여러 구간에 걸친 비용은 적용 구간의 거리에 비례해 배정하고 배정 결과를 보여준다. 대상 구간의 총거리가 0이면 사용자가 배분 대상을 직접 확인하도록 한다. 동일 비용을 전체 비용과 구간 비용에 중복 합산하지 않는다.

### 원 단위와 불변 조건

구현은 Decimal 또는 고정 소수점으로 계산한다. 구간 원시비용을 원 단위로 반올림한 뒤 정수 비용을 나눈다. 균등 배분의 나머지 원은 저장된 참여자 ID 순서로 1원씩 배정한다. 추가 비용의 거리 비례 배정은 소수 잔여가 큰 구간부터 1원씩 주고, 동률은 구간 순서로 처리한다.

- 구간별 개인 부담액 합계는 해당 구간 비용과 정확히 같아야 한다.
- 전체 개인 부담액 합계는 전체 구간 비용 합계와 정확히 같아야 한다.
- 탑승하지 않은 구간의 비용을 배정하지 않는다. 명시적으로 선택한 공동 비용은 예외로 근거를 표시한다.
- 같은 입력·규칙·버전이면 같은 결과가 나와야 한다.
- 잘못된 거리, 0 이하 연비, 음수 비용, 중복 비용으로 정산을 확정할 수 없어야 한다.

### 기준 예시 · 모든 수치는 가상 데이터

연비 12km/L, 유가 1,800원/L이면 1km당 추정 유류비는 150원이다. 운전자를 포함하고 추가 비용은 없는 상황이다.

| 구간 | 누적거리 | 분담 대상 | 추정 비용 | 개인 배분 |
| --- | --- | --- | --- | --- |
| 1 | 1,000 → 1,010km | D, A, B | 1,500원 | 각 500원 |
| 2 | 1,010 → 1,020km | D, B | 1,500원 | 각 750원 |
| 합계 | 20km | D, A, B | 3,000원 | D 1,250원 / A 500원 / B 1,250원 |

운전자가 받는 금액은 A의 500원과 B의 1,250원을 합한 **1,750원**이다. 세 사람에게 전체 비용을 똑같이 나누면 각 1,000원이므로, 중간 하차자의 금액이 어떻게 달라지는지 설명할 수 있다.

같은 예시에서 운전자를 제외하면 A는 750원, B는 2,250원을 부담한다. 두 방식 모두 구현 검증의 기준값으로 사용한다.

위 수식과 예시는 플랫폼 수수료가 0원인 MVP 기준이다. 유료화 시에도 공동 운행비의 구간 배분은 유지하고, 플랫폼 수수료와 운전자 실수령액을 별도 항목으로 계산·표시한다. §12의 차감 예시는 운전자 수령 예정 정산금에서 수수료를 빼는 모델이며, 수수료 부담 주체는 유료화 전에 확정한다.

### ‘왜 이 금액인가요?’ 개인 영수증 디자인

사용자 지정 방향은 개인 영수증을 감각적인 화면으로 보여주는 것이다. **내가 보낼 금액 → 내가 탄 구간 → 함께 나눈 사람 → 계산 근거**를 연결하고, 자세한 원가·계산식은 필요할 때 펼쳐 본다. 금액은 정지된 상태에서 바로 읽을 수 있게 한다.

| 검토 시안 | 시각 방향 | 정보 구조 |
| --- | --- | --- |
| 동행 티켓 · 추천 검토안 | 웜 화이트 티켓, 딥 틸 타이포그래피, 민트색 탑승 구간, 절취선 형태의 구분 | 500원 → 전체 20km 중 내 10km → 운전자 포함 3명 → 1,500원 ÷ 3명 |
| 여정 노트 | 여백이 넓은 편집형 구성과 세로 구간 기록 | 함께한 20km 중 내 10km → 탑승 구간 500원·하차 후 구간 0원 → 보낼 금액 500원 |

두 안은 **동승자 모바일 웹** 정산표의 검토용 방향이며 최종 선택은 아직 하지 않았다. 차량 본체 화면은 §5의 확장·분할 창 기준으로 별도 설계한다. 브랜드 색상은 §2를 따른다. 실제 앱에서는 현재 정산 버전·데이터 출처·운전자 포함 여부를 표시하고, 유류비의 추정 여부와 통행료·주차비·수수료를 구분한다. 운전자 수수료를 동승자의 부담으로 잘못 표시하지 않는다.

송금 수단은 영수증 확인 후 카카오페이·토스로 선택하며, 미검증 수단의 처리 기준은 §7을 따른다. 광고는 영수증 본문과 분리된 하단 또는 넓은 화면의 옆 영역에 배치한다. 작은 화면·긴 별칭·여러 탑승 구간에서도 금액·단위·버튼이 잘리지 않아야 한다. 검토용 시안의 송금 동작은 실제 이체와 구분한다.

## 7. 정산 수단 · 카카오페이·토스페이와 QR

**동행 참여 QR → 모바일 정산 페이지 → 정산 수단 선택 → 외부 송금·결제 화면**의 순서로 구성한다. 참여 링크와 수취 링크는 목적과 접근 권한을 구분한다.

### 서비스별 적용

정산 수단의 기획 범위에 **카카오페이와 토스페이**를 포함한다. 운전자가 사용할 수취 수단을 등록하고, 동승자는 사용 가능한 수단을 선택한다. 서비스마다 제공하는 기능과 검증 상태를 저장한다.

| 서비스·방식 | 적용 계획 | 연동 확인 기준 |
| --- | --- | --- |
| 카카오페이 개인 송금 | 수취 링크를 이용한 MVP 송금 연결 | 링크 발급·열림과 수취인 확인, 금액 복사, 수동 수취 확인 |
| 토스 개인 송금 | 토스 계열의 MVP 송금 연결 | 공식 지원 링크·앱 연결 방식을 확인하고 실제 기기에서 검증한 뒤 활성화. 미검증 시 계좌·금액 복사 안내 제공 |
| 토스페이 가맹점 결제 | 정식 결제 연동 후보 | 이용 조건·수취 구조를 확인한 뒤 결제 생성·인증·승인·결과 처리를 별도로 구현 |

토스페이 공식 가이드는 가맹점이 생성한 결제의 `checkoutPage`로 구매자를 보내는 흐름을 안내한다. 이 문서에서는 이를 근거로 **토스페이 결제 연동과 개인 간 토스 송금 연결을 구분**한다. 가맹점 결제가 운전자 개인에게 직접 송금하는 기능을 제공한다고 가정하지 않는다. [토스페이 연동 가이드][toss-pay], [결제창 연결][toss-checkout]

모바일의 개인 정산 버튼은 ‘카카오페이로 송금’, ‘토스로 송금’으로 표현한다. ‘토스페이로 결제’는 정식 결제 연동을 검증한 경우에 사용한다. 수취인이 해당 수단을 등록하지 않았거나 연결이 검증되지 않았다면 송금 버튼을 활성화하지 않는다.

### MVP 공통 처리

| 항목 | MVP 처리 |
| --- | --- |
| 수취 링크 | 운전자가 등록하고 실제 휴대폰에서 열림을 검증한 링크 사용 |
| 정산 금액 | 탄만큼 페이지에서 명확히 표시하고 복사 기능 제공 |
| 금액 자동 입력 | 제공되는 것으로 가정하지 않음. 비공식 URL 파라미터 사용 금지 |
| 송금 실행 | 사용자가 외부 서비스에서 직접 확인·실행 |
| 링크 클릭·외부 앱 복귀 | 송금 완료로 간주하지 않음 |
| 완료 표시 | 동승자의 ‘보냈어요’와 운전자의 ‘수취 확인’을 별도로 기록 |
| 수취 링크 실패·미등록 | 정산표를 유지하고 운전자가 제공한 수동 송금 안내 제공 |

정산 수단을 바꿔도 개인 부담액과 정산 버전은 유지한다. 수단별 클릭 기록을 별도 채무로 만들지 않으며, 수취 완료한 금액을 다른 수단으로 다시 요청하지 않는다. MVP의 수동 수취 확인 원칙은 카카오페이와 토스 개인 송금에 동일하게 적용한다.

### 카카오페이 확인 사항

공식 FAQ는 사용자가 직접 발급하는 ‘코드송금 받기’와 제휴 사업자의 ‘코드송금 API’를 구분한다. 공식 포럼의 2024년 답변은 금액 지정 URL 생성을 지원하지 않는다고 안내하고, 2025-07-31 답변은 코드송금 API의 일시 중단을 안내한다. **이 과거 공지만으로 현재 제휴 상태를 확정하지 않는다.** 제휴 가능 여부와 완료 콜백은 별도 확인 과제로 남긴다. [방식 구분][kakao-types], [금액 지정 제약][kakao-amount], [API 중단·콜백 안내][kakao-status]

개발자센터 운영정책상 코드송금 받기·정산하기는 비상업적 개인 간 용도로 안내된다. 공모전 시연의 수취 링크를 검증하고, 출시·사업화의 이용 조건은 별도로 확인한다. [운영정책][kakao-policy]

광고 수익화 단계부터 해당 송금 상품의 상업적 서비스 내 이용 조건을 확인한다. 현재의 운전자 직접 송금 경로에는 플랫폼이 수수료를 자동 분리 수납하는 기능이 설계되어 있지 않다. 유료화 단계에서는 결제·정산 제휴의 분리 지급 또는 별도 수수료 청구 구조를 설계하고, 실제 수납·취소·환불 처리를 검증한다. 정산표에 100원을 적는 것만으로 플랫폼 매출이 발생했다고 기록하지 않는다.

시연에서 실제 송금을 하지 않았다면 ‘송금 화면 연결’까지만 보여준다. 수동으로 확인한 상태에는 ‘운전자 확인’이라는 근거를 남긴다.

## 8. 구현 구조와 데이터

### 구성 기본안

```text
Pleos Vehicle SDK ──→ 차량 데이터 어댑터 ──→ 구간·정산 로직 ──→ 차량 UI
                                               │
                                           로컬 저장소
                                               │ 동기화
                                         최소 공유 서버
                                               │
                                 동승자 모바일 웹 ──→ 외부 송금 서비스
```

| 구성 | 기본 선택과 책임 |
| --- | --- |
| 차량 앱 | Kotlin / Android Automotive OS, 차량용 화면과 주차 중 확인 흐름 |
| 데이터 어댑터 | SDK 연결, Capability, 단위 변환, 오류·재연결 처리 |
| 동행 이력 수집 | ACTIVE 동안 시간–누적거리 저장, 주차 기록·수집 공백·재연결 관리. 선택 도어·위치는 정차 후보와 짧은 위치 수집으로 추가 |

| 로컬 저장 | Room 등으로 동행·확정 구간·이벤트를 먼저 저장 |
| 모바일 웹 | 앱 설치 없이 별칭 등록, 개인 정산 근거, 카카오페이·토스 수단 선택, 금액 복사·송금 연결 |
| 공유 서버 | 참여 토큰, 등록 요청, 정산 버전과 수동 확인 상태 동기화 |

UI 라이브러리, 웹 프레임워크, 서버·DB 제공자는 아직 선택하지 않았다. 기본 구조는 차량의 구간 확정을 기준으로 삼는다. 모바일의 참여·하차 요청만으로 거리를 확정하지 않는다. 네트워크가 끊겨도 차량 기록은 로컬에 남기고, 공유가 지연되고 있음을 표시한다.

후속 좌석 기능에서 사람별 좌석 상태가 필요할 때만 `SeatBinding`(확인한 참여자·좌석 영역, 연결 유효 구간·출처)을 추가한다. 점유 신호만으로 연결을 생성·재활성화하지 않으며 좌석 이동 시 이전 연결을 종료한다. 이 모델은 MVP 저장 구조의 필수 요소가 아니다.

수익화 단계의 추가 모델은 `AdPlacement`(광고 위치·스폰서·소재·노출 이벤트), `FeePolicy`(적용 시작일·과금 단위·금액·부담 주체·버전), `FeeTransaction`(정산 ID·정책 버전·실제 수납·취소·환불·운전자 지급액)으로 분리한다. MVP에는 과금 없이 광고 목업과 수수료 0원 표시만 사용한다.

### 상태와 수정

```text
DRAFT → ACTIVE → REVIEW → SHARED → CLOSED
   └──────→ CANCELLED
```

- `DRAFT`: 명단·규칙을 준비한다. 유효한 출발 거리와 탑승자 확인 후 `ACTIVE`로 간다.
- `ACTIVE`: 탑승자 변경 경계마다 구간을 저장한다. 종료 거리 확인 후 `REVIEW`로 간다.
- `REVIEW`: 구간·비용·대상자를 검토한다. 유효성 검사와 사용자 확정 후 `SHARED`로 간다.
- `SHARED`: 확정 버전의 정산표를 공유한다. 수취 확인 또는 미수금 처리 선택 후 동행을 닫는다.
- `CLOSED`: 확정 기록을 보관한다. 동행 종료와 전원 송금 완료는 별도 상태로 표현한다.
- `CANCELLED`: 생성 취소 또는 진행 중 동행 폐기 사유를 남긴다. 외부 송금 취소·환불을 의미하지 않는다.

위 상태는 동행 전체의 상태다. 개인 RideSession의 하차 확정과 개인 Settlement의 잠정→검토→확정은 별도로 관리하며, ACTIVE 상태에서도 먼저 하차한 사람의 기록·페이지가 존재할 수 있다.

공유 후 수정은 이전 버전을 남기고 새 정산 검토 버전을 만든다. 이전 링크에는 수정 검토 상태와 확정된 최신 버전을 안내하며 검토 중에는 이전 금액의 새 송금 안내를 보류한다. ACTIVE 동행의 개인 정산 수정은 동행 전체 상태와 별도로 처리한다. 실제 송금·수취 기록은 보존하고, 변경된 부담액과 이미 받은 금액의 차이를 보여주며 수동 추가 정산으로 연결한다. 수정으로 과거 입금을 지우거나 자동 환불하지 않는다.

## 9. 오류·예외 처리 기준

| 상황 | 처리 |
| --- | --- |
| 좌석 점유 미지원·불일치 | 확인된 명단을 기준으로 진행한다. 센서가 사람을 식별했다고 표현하지 않는다. |
| 짐·사람 미연결 좌석의 Occupied | 센서만으로 사람·탑승 기록·분담 인원을 추가하지 않는다. 확인된 명단과 확정 경계에 따른 금액 유지 |
| Odometer 권한 거절·미지원 | 차량 데이터 모드를 사용할 수 없음을 표시한다. 수동/모의 모드는 출처를 구분한다. |
| 조회 지연·실패 | 경계 확정을 보류한다. 확정 전 이동이 재개되면 자동으로 뒤 시점의 값을 소급 적용하지 않는다. |
| 누적거리 감소·비정상 도약 | 구간을 검토 대상으로 남긴다. 음수 거리나 임의 보정으로 확정하지 않는다. |
| 0km 구간 | 유류비는 0원이다. 명시적인 주차비 등 추가 비용만 별도로 처리한다. |
| 하차 확인 누락 | §5의 시간·주차 기록 선택으로 거리 후보를 찾는다. 위치 연동 시 실제 방문 후보도 제공한다. 사용자 확인 후 전체 분담 재계산, 경계 미합의는 검토 중 유지 |
| 시간·위치 이력 공백 | 과거 기록이 있는 것처럼 보간·복원하지 않는다. 유효한 기록 범위를 표시하고 보조 수동 보정·검토로 연결한다. |
| 중복 탭·네트워크 재전송 | 이벤트 ID로 중복 구간·참여자·비용 생성을 막는다. |
| 앱 종료·재실행 | 확정된 이벤트와 구간을 복원하고 마지막 미완료 경계를 다시 확인한다. |
| 공유 서버 연결 끊김 | 차량 로컬 저장을 유지한다. 동승자 화면에 동기화 지연·정산 버전을 표시한다. |
| 빈 탑승자 목록 | 나눗셈을 수행하지 않고 구간 확정을 막는다. |

기본 수집 정보는 별칭, 참여 토큰, 동행 중 시간–누적거리 이력·주차 기록, 구간 거리, 비용과 정산 상태다. 이력은 동행 중에만 로컬 수집하고 개인 페이지에는 수정에 필요한 후보만 제공한다. 수정 가능 기간과 이력 보관·삭제 시점을 정한다. P0에 연속 위치 기록, 연락처, 금융 계정 인증정보는 필요하지 않다. 위치 기능 추가 시 기록 범위·보관 기간·개인별 노출을 별도로 정한다. 공유 토큰에는 만료·권한 범위를 두고, 동승자는 다른 사람의 정보를 수정할 수 없게 한다. 로그·영상·저장소에 실제 수취 정보나 비밀 키를 포함하지 않는다.

## 10. 개발 순서와 완료 조건

공식 설치 문서는 Android API 28 이상, Gradle 8.0 이상, Java/Kotlin을 안내한다. 작성일에 확인한 Vehicle SDK 의존성 예시는 `ai.pleos.playground:Vehicle:2.3.2`다. 설치 시 공식 문서와 실제 해석된 의존성을 대조하고, 검증한 버전을 고정한다. [에뮬레이터 설치][pleos-setup], [SDK 의존성][pleos-dependency]

공모전의 [개발 환경 가이드][contest-development]도 같은 최소 환경을 안내하며, SDK별 현재 제공 상태와 사용 조건을 확인하도록 한다. FAQ에 따라 **접수양식 5번 ‘개발 계획’**에는 Pleos Connect 구현 방식, 개발 범위, SDK/API 사용 계획을 구체적으로 적는다. 탄만큼은 §4·§8·§10의 내용을 해당 항목에 연결한다. [공식 FAQ][contest-faq]

- [ ] 개인 하차 확정 후 동행 ACTIVE 유지, 잠정/확정 금액 구분, 오조작 취소·거리 조회 실패·중복 클릭 처리
- [ ] A의 하차 누락으로 전원 20km·각 1,000원인 기록을 A 10km로 수정하면 D 1,250원 / A 500원 / B 1,250원, 총 3,000원 유지
- [ ] 하차 버튼을 누르지 않은 시각을 선택하면 당시 유효한 거리 기록을 제시. 시간 비율로 거리·금액 배분하지 않음
- [ ] 주차 기록은 선택 후보만 제공하고 자동 하차하지 않음. 이력 수집 점이 늘어도 구간 분할·반올림·금액 결과 유지
- [ ] 시간 선택·근접값·보간·수동 보정의 출처와 추정 범위 표시, 원본 SDK 관측값 보존. 공백·시계 변경·경계 미합의는 검토 중 유지
- [ ] 시작/종료 역전·동행 거리 범위 초과·같은 사람의 재탑승 중복 거부, ACTIVE 동행의 과거 구간 수정 후 진행 상태 유지
- [ ] 동승자의 본인 수정 요청→운전자 확인, 수정 이력·관련자별 전후 금액 표시. 검토 중 이전 금액의 새 송금 안내 보류
- [ ] A의 1,000원 수취 확인 후 부담액을 500원으로 수정하면 기존 수취 1,000원과 돌려줄 500원 표시, 자동 환불 없음
- [ ] 1원 단위 잔액이 생겨도 개인 합계와 총비용 일치
- [ ] 0km, 운전자 단독, 연비 0, 누적거리 감소, 권한 거절 처리
- [ ] 중복 요청, 오프라인 복구, 공유 후 수정과 기존 수취 기록 보존
- [ ] 주행 제한 시 차량 조작 차단, 해제 후 상태 복원
- [ ] 송금 링크 클릭·앱 복귀가 수취 완료로 바뀌지 않음
- [ ] 카카오페이·토스 선택 전환 시 금액·정산 버전 유지, 미검증 수단 안내, 중복 요청 방지

### 선택 기능 추가 시 검증 · MVP 완료와 분리

- [ ] 실제 방문한 장소의 위치·시각·거리 연결, 동일 장소 반복 방문 후보 선택, 위치 차단·오래된 값·공백 시 시간 선택으로 안내. 지도 최단거리로 실제 주행거리 대체 없음
- [ ] 정차·도어 이벤트 후보 생성, 초기 상태·반복 개폐·여러 문 이벤트 중복 억제, 짐 꺼내기·문만 열기·휴게소 정차로 명단·구간·금액 자동 변경 없음
- [ ] 짧은 위치 구독의 성공·시간 초과·이동 재개 시 해제, 오래된 캐시·다음 이동 지점 위치의 잘못된 연결 방지, 위치 실패에도 시간·거리 후보 유지
- [ ] Seat 미지원·일시적 Empty·좌석 이동으로 개인 하차·금액을 자동 확정하거나 취소하지 않음
- [ ] 운전자 포함 등록 3명·점유 2자리에서 확인 안내만 표시하고 명단·구간·금액 유지. 비교 범위 불일치·null·미지원은 확인 불가로 처리
- [ ] D·A 두 사람만 등록한 상태에서 미연결 좌석의 Occupied를 켜고 꺼도 분담 인원 2명과 기존 개인 금액 유지
- [ ] A 하차 확정 후 같은 좌석에 짐의 Occupied 신호가 남아도 A의 기록·금액 유지, 재탑승 기록 자동 생성 없음
- [ ] 동일 명단·확정 경계·비용 입력에 대해 센서 켜기/끄기·짐 이동·점유 노이즈·캐릭터 반응이 정산 결과를 바꾸지 않음
- [ ] 광고 로딩 실패·차단 또는 거리 애니메이션 종료 전에도 정산 확인·송금 가능
- [ ] 주행거리 연출의 최종값이 확정 구간 합계와 같고, 차량 주행 제한 시 광고·장식 애니메이션 중단
- [ ] 유료화 전환 시 정산금·수수료·운전자 실수령액 일치, 중복 차감 방지·취소/환불 정책 검증

## 11. 에뮬레이터 시연 플레이북

Virtual Console은 Odometer를 1km 단위로 설정하고 좌석별 점유, 기어 상태를 바꿀 수 있다. 아래 MVP **예정 시나리오**에서는 Odometer·주행 제한 상태를 사용하며 좌석 상태 조작·조회는 필요하지 않다. [Virtual Console 사용 가이드][pleos-console]

| 순서 | 조작 | 화면·기록에서 확인할 것 |
| --- | --- | --- |
| 1 | 주차 상태, Odometer 1,000km 설정 | 제한 상태 확인, 연비 12km/L·유가 1,800원/L 입력 |
| 2 | D·A·B 등록 후 출발 확정 | SDK 출발값과 탑승자 3명 저장 |
| 3 | 주행 상태로 변경, Odometer 1,010km 설정 | 조작 잠금과 저장 상태 유지 |
| 4 | 주차 상태로 복귀, A가 앉아 있는 동안 `[A 내려요]` 선택 | 10km·3명 구간 확정, A 개인 페이지·QR 확인, 다음 구간은 D·B |
| 5 | 주행 상태, Odometer 1,020km 설정 후 주차 | 최종 10km·2명 구간 확정 |
| 6 | 동행 종료·정산 공유 | D 1,250원 / A 500원 / B 1,250원 |
| 7 | 모바일에서 A 정산표 열기 | A의 10km·500원 근거, 카카오페이·토스 선택, 금액 복사, 검증한 외부 송금 연결 |
| 8 | 동승자 송금 표시와 운전자 수취 확인 | 자동 결제 판정 없이 상태 구분 |

별도 누락 시나리오에서는 A의 하차 버튼을 누르지 않고 이력을 수집한 뒤, 종료 후 A가 ‘하차한 시각·주차 기록’을 선택하도록 한다. 당시 거리 후보와 추정 표시를 확인하고 운전자가 반영하면 세 사람의 금액이 기준 예시로 다시 계산되는지 검증한다. 이력 공백에서는 정확한 하차 기록을 제시하지 않는다.

후속 좌석 보조를 구현하면 별도 장면으로 등록 3명·점유 2자리의 확인 안내를 보여준다. 명단은 사용자 확인으로만 수정하며 Empty만으로 개인 하차를 확정하지 않는다. A의 하차 버튼 확정·개인 QR 확인 이후 Occupied→Empty로 바뀌거나 짐의 Occupied가 남아도 구간·금액이 유지되는지 검증한다. 영상에는 Console 입력과 SDK 조회 결과를 함께 보여주고, 수동/모의 입력이 있다면 해당 장면에 표시한다.

광고 시연을 추가하면 주차 후 20km 결과가 확정된 정산표 옆에서 거리 숫자가 0→20km로 올라가고 스폰서 캐릭터가 짧게 이동하는 장면을 보여준다. 광고 목업임을 표시하고, 실제 광고 계약·수수료 수납을 완료한 것처럼 설명하지 않는다.

## 12. 기획서·발표·홍보영상

### 발표 논리

1. 친구 A는 중간에 내렸는데 전체 비용을 똑같이 나눠도 되는가?
2. 차량의 실제 거리와 탑승 구간을 연결하면 계산 근거를 만들 수 있다.
3. Pleos Odometer 변화에 따라 구간과 개인 금액이 달라지는 것을 보여준다.
4. 각자 모바일에서 근거를 확인하고 송금 화면으로 이동한다.
5. 초기에는 정산 화면·캐릭터 광고로 수익화하고, 반복 이용이 정착되면 건당 수수료 모델로 확장한다.

| 1차 필수 심사 항목 | 공식 평가 관점 | 탄만큼이 준비할 설명과 증거 |
| --- | --- | --- |
| 차량 특화성 | 모바일 대비 차량 환경의 가치, 주행·정차 맥락과의 결합 | 차량 누적거리가 계산에 쓰이고 주차 중 탑승자 확인으로 구간이 확정되는 시연 |
| 창의성 | 독창성, 명확한 불편·요구와 해결 방식 | 중간 하차 시 일괄 균등 정산과 달라지는 금액·근거 비교 |
| 기술 활용성 | SDK·API가 핵심 기능과 경험에 기여하는 정도 | Odometer 조회→구간 생성→금액 계산의 연결, 권한·오류·복구 검증 |
| 사업성 | 타깃, 사용자 확보, 지속 이용과 확장 가능성 | 초기 모집 경로·예상 MAU·재이용 지표, 광고에서 건당 수수료로 이어지는 수익화 단계 |

네 항목은 모두 필수 평가이며 세부 배점은 공개되지 않았다. 개발 산출물의 단계별 가산점은 별도로 적용된다. 임의의 항목별 비중이나 가산점 수치를 만들지 않는다. 2차 PT 세부 기준은 추후 공지 대상이다. [심사·시상 가이드][contest-judging]

### 사업성 자료의 구현 기본안

- 초기 확보: 기존 친구 여행·동료 카풀 그룹의 운전자를 모집하고, 동승자는 참여 QR로 유입시킨다.
- 예상 MAU: 모집 가능한 운전자 수, 동행 수, 동행당 인원, 중복 참여율을 가정표로 제시한다. 아직 실측값은 없다.
- 재이용: 첫 동행 완료 사용자가 30일 안에 새 동행을 완료한 비율을 코호트별로 관찰한다. 관찰 기간과 분모를 함께 적는다.
- 확장: 여행 동행 검증 후 반복 카풀·동호회로 넓힌다. 사용 빈도·정산 수용성·운전자와 동승자의 부담을 인터뷰한다.

이는 공식 사업성 항목에 답하기 위한 자체 검증 계획이다. 시장 규모·만족도·매출을 검증된 수치처럼 제시하지 않는다. 수익화 방향은 아래 사용자 지정 모델을 따르고, 단가·전환 시점은 실제 수요로 검증한다.

### 수익 모델 · 광고에서 정산 수수료로

**사용자 지정 방향:** 초기에는 정산 화면 옆 광고와 주행거리 누적 애니메이션 속 캐릭터 광고로 수익을 만들고, 사용자가 늘고 서비스가 정착되면 정산금 일부를 플랫폼에 귀속한다. 건당 100원은 후속 수수료의 예시다.

| 단계 | 수익원 | 상품 구성 | 도입 판단 |
| --- | --- | --- | --- |
| 초기 · 정산 무료 | 정산 화면 광고 | 개인 정산표 옆의 배너·브랜드 카드. 모바일은 화면 크기에 따라 정산표 아래 배치 | 광고 수요·실제 유효 노출·정산 완료율 검증 |
| 초기~성장 | 캐릭터 스폰서십 | 거리 숫자가 올라가는 동안 캐릭터의 의상·소품·배경·도착 연출에 브랜드 적용 | 캐릭터 호감도·브랜드 인지도·재이용 영향 검증 |
| 이용자 정착 후 | 정산 건당 정액 수수료 | 정산금에서 예를 들어 100원을 플랫폼에 귀속 | 반복 이용·지불 의향·수수료 수납 구조 검증 후 전환 |

수수료 전환은 MAU, 정산 완료 건수, 30일 재이용률, 유료화 수용성을 보고 결정한다. 아직 전환 기준의 숫자나 도입 날짜는 확정하지 않았다. 광고와 수수료를 병행할지, 유료 이용자 광고를 줄일지도 후속 실험으로 결정한다.

### 광고·거리·캐릭터 경험의 기본안

- 거리 연출은 **확정된 이번 동행 거리**를 누적해서 보여준다. 예를 들어 숫자가 0→20km로 올라가며 캐릭터가 경로를 따라 도착한다. 계기판 누적거리 원본과 개인 탑승 구간은 별도로 정확하게 표시한다.
- 스폰서 캐릭터나 브랜드 소품을 연출에 넣고 ‘광고’ 또는 ‘스폰서’임을 표시한다. 캐릭터의 구체적인 외형·이름은 아직 정하지 않았다.
- 정산표, 금액 복사, 송금 버튼은 즉시 사용할 수 있게 한다. 광고 시청·클릭이나 애니메이션 종료를 정산의 조건으로 두지 않는다.
- 차량에서는 주차 중에 짧게 한 번 재생한다. 동승자 모바일에서도 반복 재생을 기본으로 두지 않고, 동작 줄이기 설정에서는 최종 거리와 정지 캐릭터를 보여준다.
- 거리 데이터는 정산 근거와 연출에 사용한다. 주행거리 증가만으로 광고 노출 매출이 발생한 것으로 계산하지 않는다.

### 건당 100원 수수료의 계산 기본안

‘건당’이 동행 정산 1건인지 개인 송금 1건인지와 부담 주체는 유료화 전에 확정한다. 아래는 **동행 정산 완료 1건당 100원을 운전자 수령 예정 정산금에서 차감**하는 설명용 가정이다. 동승자에게 추가로 100원을 청구하는 모델로 바꾸지 않는다.

```text
동승자 송금 합계                 1,750원
플랫폼 귀속 수수료                100원
운전자 실수령액                 1,650원
동승자 송금 합계 = 운전자 실수령액 + 플랫폼 귀속 수수료
```

이 예시에서는 운전자가 수수료를 부담하므로 정산 확정 전에 이를 보여준다. 실제로 100원을 받을 수 있는 제휴·수납 구조를 검증한 뒤 적용한다. 정산금이 수수료보다 작거나 취소·부분 정산되는 경우의 면제·환불 기준도 확정한다. 같은 동행의 재열기·수정·송금 수단 변경으로 수수료를 중복 차감하지 않는다.

### 수익성 검증

```text
노출형 광고 매출 = 유효 광고 노출 수 / 1,000 × 실제 계약 eCPM
스폰서십 매출 = 계약으로 확정한 캠페인·캐릭터 사용 대가
수수료 매출 = 실제 수납한 유료 정산 건수 × 건당 수수료
```

모두 산식이며 현재 매출이나 광고 단가의 실측값은 없다. 같은 광고 계약을 노출형·스폰서십 매출에 중복 계상하지 않는다. 결제·정산 비용과 광고 운영·캐릭터 제작·서버 비용을 차감해 수익성을 확인하고, 광고 도입 및 유료화 전후의 정산 완료율·재이용률도 함께 본다.
